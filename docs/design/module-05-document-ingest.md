## 0. 结论摘要

| # | 决策 | 重要度 |
|---|---|---|
| 1 | 只支持 **PDF / Markdown / TXT**，Tika 统一解析；docx、OCR 不做 | ★★★★★ |
| 2 | 异步走 **RocketMQ**：`parse` → `embed` 两个 topic，两个消费组 | ★★★★★ |
| 3 | **不用 `rocketmq-spring-boot-starter`**，用原生 `rocketmq-client` 自己包一层 | ★★★★★ |
| 4 | 队列做**接口抽象**，另提供 `local` 直调实现：单测/集成测试**完全不需要 MQ** | ★★★★★ |
| 5 | **先落库再发消息** + 启动/定时对账补发；不引 outbox 表（记为已知限制） | ★★★★★ |
| 6 | 切块按 **token**：400 token / 重叠 60；用 jtokkit 近似，`TokenCounter` 接口隔离 | ★★★★★ |
| 7 | 向量列 `vector(1024)`，`cast(#{embedding} as vector)` 文本绑定，不改驱动 scope | ★★★★★ |
| 8 | 原文存本地目录，DB 存 sha256 + 路径 + **归一化全文** | ★★★★ |
| 9 | 去重用 sha256 部分唯一索引（`WHERE deleted = FALSE`），重复上传返回已有文档 | ★★★★ |
| 10 | 并发：重复上传撞唯一索引要回查；处理中 reindex/删除 → 409 | ★★★★ |
| 11 | 每批 embedding 独立事务（拆独立 Bean，别靠自调用） | ★★★★★ |
| 12 | 本模块**不接入对话**，`ChatService` 一行不改 | ★★★★★ |

一句话：**模块五的产出是「一批可检索、可核对、可重跑的分块」，并且这条链路要经得起 MQ 的重复投递和进程随时被杀。**

## 1. 目标与边界

### 1.1 目标

1. `POST /api/documents` → 校验 → 落盘 → 写 `document(PENDING)` → 发 RocketMQ 消息 → 202。
2. 消费端：解析 → 归一化 → 按 token 分块 → 落库（`embedding = NULL`）→ 发 `embed` 消息。
3. 消费端：按批调 embedding → 回填 → `READY`。
4. 任何一步失败：按 MQ 重试 3 次；仍失败则 `FAILED` + `error_message`，`POST /{id}/reindex` 可重跑。
5. 进程重启不丢任务：未确认的消息由 RocketMQ 重投；已落库但没发出消息的由对账任务补发。
6. 可核对：`GET /{id}/chunks` 能看到正文、标题、字符偏移、token 数。

### 1.2 不做

- **不做 OCR / 表格结构化 / docx**（同上版）。
- **不做顺序消息**：同一文档的消息天然只有两条，且 embed 消息在 parse 成功后才发，不需要全局顺序。
- **不做事务消息**：会引入 half-message 回查，收益不抵复杂度。用「先落库 + 对账」替代。
- **不做 outbox 表**：这是严格做法，留作 v2 改进点，本模块用对账兜住。
- **不做 DLQ 自动补偿**：DLQ 只作为排查入口；自动重投可能无限烧 embedding 预算。
- **不做消费者水平扩容**：单实例；多实例下同一文档可能被并发消费，靠幂等能扛但没验证过，明确记为限制。
- **不做 RocketMQ Dashboard**：排查先用消费日志和 `mqadmin`；需要看图了再加容器。
- **不接入对话**（模块六）。

### 1.3 交付物

- `document/` 包：entity / mapper / service / parser / chunker / storage / queue
- `controller/DocumentController`
- `V2__create_document.sql`
- `docker/rocketmq/broker.conf` + `docker-compose.yml` 增加 namesrv/broker
- 测试 6 类 + 验证文档

## 2. 数据模型（V2）

```sql
-- V2: 文档与文档分块
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE document (
    id              BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    title           VARCHAR(200) NOT NULL,
    file_name       VARCHAR(255) NOT NULL,
    mime_type       VARCHAR(100) NOT NULL,
    file_size       BIGINT       NOT NULL,
    storage_path    VARCHAR(500) NOT NULL,
    content_sha256  CHAR(64)     NOT NULL,
    normalized_text TEXT,                                  -- 解析并归一化后的全文
    status          VARCHAR(20)  NOT NULL DEFAULT 'PENDING',
    chunk_count     INT          NOT NULL DEFAULT 0,
    char_count      INT          NOT NULL DEFAULT 0,
    token_count     INT          NOT NULL DEFAULT 0,
    retry_count     INT          NOT NULL DEFAULT 0,       -- 对账补发次数
    last_progress_at TIMESTAMPTZ NOT NULL DEFAULT now(),   -- 心跳：状态切换、每批写完都要刷
    chunk_truncated BOOLEAN      NOT NULL DEFAULT FALSE,
    error_message   VARCHAR(500),
    created_at      TIMESTAMPTZ  NOT NULL DEFAULT now(),
    updated_at      TIMESTAMPTZ  NOT NULL DEFAULT now(),
    deleted         BOOLEAN      NOT NULL DEFAULT FALSE
);

CREATE UNIQUE INDEX uk_document_sha256_active ON document (content_sha256) WHERE deleted = FALSE;
-- 对账任务按它扫。注意：不能用 updated_at，见 4.5
CREATE INDEX idx_document_status_progress ON document (status, last_progress_at);

CREATE TABLE document_chunk (
    id              BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    document_id     BIGINT      NOT NULL REFERENCES document (id) ON DELETE CASCADE,
    chunk_index     INT         NOT NULL,
    content         TEXT        NOT NULL,
    heading         VARCHAR(500),
    char_start      INT         NOT NULL,
    char_end        INT         NOT NULL,
    char_count      INT         NOT NULL,
    token_count     INT         NOT NULL,
    embedding       vector(1024),
    embedding_model VARCHAR(64),
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE UNIQUE INDEX uk_document_chunk_index ON document_chunk (document_id, chunk_index);
CREATE INDEX idx_document_chunk_pending ON document_chunk (document_id) WHERE embedding IS NULL;
CREATE INDEX idx_document_chunk_embedding ON document_chunk USING hnsw (embedding vector_cosine_ops);
```

三个新列的理由：

- **`normalized_text`**：`reindex` 直接读它，不再过 Tika；`char_start/char_end` 才有实际含义。不能出现在任何响应里。
- **`token_count`**（document 与 chunk 各一份）：估算成本、判断是否撞 `max-chunks`、排查「为什么这块特别长」。
- **`retry_count`**：对账补发的次数上限，防止「MQ 重投 + 对账补发」叠加成无限循环。
- **`last_progress_at`**：对账的活性判据。**不能用 `updated_at`**——消费过程中它根本不刷新，一份正在慢慢 embedding 的大文档会被误判成卡住（详见 4.5）。

`char_start/char_end` 以 **code point** 计（与 PG `char_length` 一致）；`token_count` 用 jtokkit 计，两者口径不同，不要互相换算。

## 3. 调用链

```
POST /api/documents (multipart)
   │  校验 → sha256 → 落盘 → insert document(PENDING)  ← 事务提交
   │  提交之后再 producer.send(parse)
   ▼
202 {id, status:PENDING}
   │
   │  ┌──────────── RocketMQ: doc-ingest-parse ────────────┐
   └─►│ consumer group: recordandgrow-doc-parse-consumer   │
      │                                                    │
      │  status=PARSING                                    │
      │  Tika 解析（超时 60s）→ 归一化 → 存 normalized_text │
      │  TokenCounter + Chunker → N 块                     │
      │  delete 旧 chunk（幂等）→ 批量 insert(embedding=null)│
      │  status=EMBEDDING                                  │
      │  producer.send(embed)  ─────────────────────────┐  │
      └─────────────────────────────────────────────────┼──┘
                                                        │
      ┌──────────── RocketMQ: doc-ingest-embed ──────────┘
      ▼
   consumer group: recordandgrow-doc-embed-consumer
      for each batch of 10 where embedding IS NULL:
          vectors = embeddingClient.embed(texts)
          update document_chunk ... cast(#{} as vector)   ← 独立事务
      status=READY, chunk_count=count(*), token_count=sum
```

失败路径：

```
listener 抛异常 → RECONSUME_LATER（最多 3 次，RocketMQ 自带退避）
第 4 次投递仍失败 → 标记 FAILED + error_message，返回 CONSUME_SUCCESS
                    （不进 DLQ，避免自动补偿烧钱；DLQ 只用于人工排查）
```

## 4. RocketMQ 设计（本模块最需要想清楚的部分）

### 4.1 为什么不用 starter

| 考虑 | 结论 |
|---|---|
| `rocketmq-spring-boot-starter` 对 Spring Boot **4** 的适配 | **未确认**。它历史上一直滞后于 Boot 大版本，Boot 4 的自动配置 API 有变动，不能赌 |
| 我们需要的能力 | 发一条消息、收一条消息、控制重试次数——就这些 |
| 项目风格 | `ChatClient` / `EmbeddingClient` 都是自己包的，接入层手写是一致的 |
| 自研成本 | 约 150 行：`@Component` 启 `DefaultMQPushConsumer`，`SmartLifecycle` 管启停 |

**结论**：用 `org.apache.rocketmq:rocketmq-client` 原生 SDK（remoting 协议，5.x broker 兼容）。

> 如果你更希望用 starter（少写代码、断言式注解），可以先花 10 分钟在 Boot 4 上跑一个最小 demo；能起来就换，起不来就按本方案。这个决定**不影响其它设计**，因为队列已经抽象成接口（4.4）。

### 4.2 Topic 与消息

| 项 | 值 |
|---|---|
| Topic（阶段一） | `doc-ingest-parse` |
| Topic（阶段二） | `doc-ingest-embed` |
| Producer Group | `recordandgrow-doc-producer` |
| Consumer Group | `recordandgrow-doc-parse-consumer` / `recordandgrow-doc-embed-consumer` |
| Message Key | `documentId`（排查时按 key 查消息轨迹） |
| Body | `{"documentId":123,"stage":"PARSE"}`（最小载荷，状态以 DB 为准） |
| 发送超时 | 3s（同步发，失败即 503） |

**Body 只放 id，不放文件内容**：消息体越小越好，且文件在磁盘、状态在 DB，消息只是一个「触发器」。

### 4.3 重试、幂等、顺序

- **重试**：`maxReconsumeTimes = 3`。RocketMQ 的重试间隔是分级的（10s/30s/1m 左右），够用，不自己实现退避。
- **幂等**（必须，因为 MQ 是 at-least-once）：
  - parse 阶段开头查 `document`：不存在 / `deleted=true` / `status=READY` → 直接 `CONSUME_SUCCESS` 返回；
  - parse 阶段可重复执行：先 `delete from document_chunk where document_id=?` 再 insert，天然幂等；
  - embed 阶段只处理 `embedding IS NULL`，重复投递不会重复花钱。
- **顺序**：不启用顺序消费。parse→embed 的先后由「parse 成功才发 embed」保证，不依赖 MQ 顺序。

### 4.4 队列抽象（决定测试成本的地方）

```java
public interface DocumentIngestQueue {
    void sendParse(Long documentId);
    void sendEmbed(Long documentId);
}
```

| 实现 | 触发条件 | 用途 |
|---|---|---|
| `RocketMqIngestQueue` | `recordandgrow.document.queue.mode=rocketmq` | 生产 |
| `LocalIngestQueue` | `mode=local` | 单测、集成测试、无 MQ 的本机调试 |

`LocalIngestQueue` 直接调 `DocumentIngestService.ingestParse(id)`，**测试不需要启动 broker**，也不需要在 CI 里跑 RocketMQ。这是本模块能保持「一键跑测试」的关键。

### 4.5 对账（补消息，不是标失败）

内存队列时代「启动时全标 FAILED」的做法，上 MQ 后应该改掉——消息可能还在 MQ 里等着重投，贸然标失败会把正常任务误杀。

**活性判据必须是 `last_progress_at`，不能用 `updated_at`。** 这是对齐时发现的一个真 bug：

> embed 阶段 2000 块 = 200 批，每批最坏 30s 超时 × 2 次尝试。一份慢的大 PDF 跑一小时是正常的，而 `updated_at` 在整个消费过程中一直是上传那一刻的值。对账会在第 10 分钟把它判成「卡住」→ 重发 parse → **parse 第一步就是 `delete 全部 chunk`**，把已经回填的向量清空重来。
>
> 若此时旧消费者还在按旧 chunk id 写，`update ... where id=?` 全部命中 0 行，最后却按表里的 count 置 READY——得到一份 **READY 但向量全空**的文档。这个结果既不报错，也查不出来。

所以：

```sql
-- 每批写完 / 每次状态切换都要刷
UPDATE document SET last_progress_at = now() WHERE id = ?;

-- 对账：启动一次 + 每 5 分钟
SELECT id, retry_count FROM document
 WHERE status IN ('PENDING','PARSING','EMBEDDING')
   AND deleted = FALSE
   AND last_progress_at < now() - interval '10 minutes';
```

- `retry_count < 3` → 按当前阶段补发（PENDING/PARSING → `sendParse`；EMBEDDING → `sendEmbed`），`retry_count + 1`
- `retry_count >= 3` → `FAILED`「多次重试仍失败，请手动重新索引」

心跳的时机：`markParsing` / `markEmbedding` / `markReady` 各一次，**外加每写完一批 embedding 一次**。单批最坏 65s 左右，10 分钟窗口对单批是安全的。

**为什么不标失败**：MQ 至少一次投递，消息可能只是慢。对账的职责是「补」，不是「杀」。

### 4.6 发消息的位置与失败处理

**发消息必须在事务提交之后**，不能写在 `create()` 里：

```java
// controller
Document doc = ingestService.create(file);   // @Transactional，返回时已提交
queue.sendParse(doc.getId());                // 失败 → 503/50302，记录已落库，对账会补
```

为什么不能写在 `create()` 内部：消息可能在事务提交前就被消费，消费端查不到这行、按幂等规则返回成功，文档于是停在 PENDING 十分钟。local 模式更糟——直接调用会把整条 parse 链路卷进上传事务，「每批独立事务」当场失效。

发送失败的处理：

- 接口返回 503/50302，让用户知道「没排上队」，而不是假装 202；
- 记录已经落库，**不删**——对账会在 10 分钟内补发；
- **重复上传的补偿**：同一内容再次上传时返回已有文档（200），但如果它还是 `PENDING`，要再 `sendParse` 一次。否则「上次发送失败 + 这次去重命中」会让它永远卡住。

> 严格做法是 outbox 表（同一事务写业务记录 + 消息记录，再由投递线程发）。本模块不做，理由：单用户、消息量极低、对账窗口足够。**写进 known-issues**，面试时主动讲。

## 5. 切块：按 token

### 5.1 Token 从哪来

`TokenCounter` 接口隔离实现：

```java
public interface TokenCounter {
    int count(String text);
    String name();   // 记进日志/验证文档
}
```

实现选 **jtokkit**（纯 Java，无 native 依赖，`cl100k_base`）：

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **jtokkit + cl100k_base** | 零 native 依赖、快、Windows 无坑 | 与 Qwen 分词器**不一致**，中文大概多算 1.5–2 倍 | **选它** |
| DJL HuggingFace tokenizers + Qwen tokenizer.json | 接近精确 | 带 native 库，Windows/打包有风险，需额外 tokenizer 文件 | 以后可换 |
| 调 DashScope 计数接口 | 精确 | 多一次网络调用，不可能按每段调 | 否 |

**关键点**：多算 = 偏保守，400 token 的块在 Qwen 那边大约只有 200–270 token，离 8192 上限很远，不会超限。要的是「块大小稳定可控」，不是「token 数与供应商完全一致」。这个偏差必须写进验证文档，别装作精确。

### 5.2 参数

| 参数 | 默认 | 说明 |
|---|---|---|
| `chunk.max-tokens` | 400 | 每块目标 token 上限 |
| `chunk.overlap-tokens` | 60 | 相邻块重叠 |
| `chunk.min-tokens` | 20 | 小于此丢弃（全文只有一块除外） |
| `chunk.max-chunks` | 2000 | 单文档上限，超出截断并置 `chunk_truncated` |
| `document.max-chars` | 2,000,000 | 解析后文本上限，超出直接 FAILED |

### 5.3 算法

1. 归一化：`\r\n|\r` → `\n`，去行尾空白，连续空行压到 2，trim。**不合并行内空格**。
2. Markdown 标题栈 → 每块 `heading`（面包屑，如 `部署 > Docker`）。
3. 递归切分：段落 → 句末标点（`。！？；!?;`）→ 超长句子按字符硬切（**按 code point，不能切在代理对中间**）。
4. 合并：顺序累加，`countTokens(累计) > max-tokens` 就收块。
5. 重叠：下一块从上一块尾部按**句子**回退，累计 token ≤ `overlap-tokens` 为止（不按字符截，否则重叠区会切断词）。
6. 记录：`char_start/char_end`（code point）、`token_count`（jtokkit 计）、`heading`。

不变式（必须写测试）：

```
normalized.substring(cp(char_start), cp(char_end)) == content
countTokens(content) == token_count
相邻块 char_start 单调递增；重叠区允许 [start,end) 相交
```

> 重叠会让相邻区间相交——这是**允许**的，但 `content` 与区间必须严格对应，不能一个含重叠一个不含。

### 5.4 和「按字符」的差别要不要担心

- 每块 token 更均匀 → 检索粒度更稳，向量更聚焦，这是升级的理由；
- 切块变慢（要数 token）→ jtokkit 单次计数在微秒级，500 段也就毫秒级，可忽略；
- 块数会变多（中文 400 token ≈ 250 字左右）→ 同一文档 embedding 调用次数增加约 1 倍，**成本上升要写进文档**。

## 6. 嵌入与写入

### 6.1 复用现有客户端

[代码] `QwenEmbeddingClient.embed()` 内部已按 `batchSize=10` 分批、按 index 重排、429 重试。**业务层只按 10 条一组调用它**，不要在外面再分批（`batchSize` 只有一处生效）。

### 6.2 向量写入

```xml
<update id="updateEmbedding">
    UPDATE document_chunk
       SET embedding = cast(#{embedding} as vector),
           embedding_model = #{model}
     WHERE id = #{id}
</update>
```

- 参数是 `"[0.1,0.2,...]"` 字符串；**float 格式化必须 `Locale.ROOT`**（否则小数点会变逗号）。
- 不改 `postgresql` 依赖 scope，不引 `PGobject`、不引 `com.pgvector`。
- ⚠️ 这是全模块唯一的 `[推断]`：**写业务代码前先用一条 SQL 或一个小测试验证 cast 能跑**。不通就停下来，退化方案是改驱动 scope + `PGobject`。

### 6.3 事务边界

- 每批 10 条 embedding → 一个独立事务写入（`DocumentChunkWriter` 独立 Bean，**不要自调用**）。
- `embeddingClient.embed()` 绝不放在事务里。
- 某批失败 → 抛异常 → MQ 重试；下次投递从 `embedding IS NULL` 继续，已完成的批次不重算。

### 6.4 未配置 key

上传时预检 `embeddingClient.isConfigured()`，未配置 → 503/50301，不落盘、不建记录、不发消息。

[代码] `EmbeddingClient` 目前没有 `isConfigured()`，加 `default` 方法，`QwenEmbeddingClient` 覆写为「key 非空」。

## 7. 接口

| 方法 | 路径 | 说明 | 状态码 |
|---|---|---|---|
| POST | `/api/documents` | multipart `file` | 202 新建 / 200 重复内容 / 409 并发冲突 / 413 / 415 / 503 |
| GET | `/api/documents` | `page/size/status` | 200 |
| GET | `/api/documents/{id}` | 详情（不含 `normalizedText`、`storagePath`） | 200 / 404 |
| GET | `/api/documents/{id}/chunks` | 分页（**不含 embedding**） | 200 / 404 |
| POST | `/api/documents/{id}/reindex` | 清 chunk 重跑 | 202 / 404 / 409 |
| DELETE | `/api/documents/{id}` | 软删 + 删 chunk + 删文件 | 200 / 404 / 409 |

`409` 的三种情况：文档正在 PARSING/EMBEDDING 时 reindex 或删除。

## 8. 错误码

| 枚举 | code | HTTP | 场景 |
|---|---|---|---|
| `DOCUMENT_BUSY` | 40900 | 409 | 处理中 reindex / 删除 |
| `PAYLOAD_TOO_LARGE` | 41300 | 413 | 超 `max-file-size` |
| `UNSUPPORTED_MEDIA_TYPE` | 41500 | 415 | 扩展名/MIME 不在白名单 |
| `DOCUMENT_PARSE_FAILED` | 42200 | 422 | 同步校验阶段解析失败、抽不出文本 |
| `QUEUE_UNAVAILABLE` | 50302 | 503 | MQ 发送失败、producer 未就绪 |

`GlobalExceptionHandler` 还需处理 `MaxUploadSizeExceededException` → 413、`MultipartException` → 400。

## 11. 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| RocketMQ broker 内存/端口占用 | 本机开发卡顿 | `JAVA_OPT_EXT` 限制 + 只在需要时 `docker compose up` |
| `brokerIP1` 配错 | 客户端连不上，报连接超时 | 写进 compose 注释；启动日志打印 namesrv 地址 |
| 消息重复投递 | 重复解析、重复 embedding（花钱） | 幂等：status 检查 + 先删后插 + 只补 NULL |
| 对账误判长文档（用 `updated_at` 判断） | 重发 parse → 清空已回填向量 → 得到 READY 但全空的文档 | **改用 `last_progress_at` 心跳**（4.5） |
| Spring Boot BOM 改写 RocketMQ 的 Netty（4.1.130 → 4.2.17） | 连接期 `NoSuchMethodError`，编译期发现不了 | 第 6 步先跑最小 demo + `mvn dependency:tree -Dincludes=io.netty`；必要时显式 pin 4.1.x（本项目用 Tomcat，Netty 只被 RocketMQ 用，pin 不影响 web 层） |
| 重复上传命中已有文档，但上次消息没发出去 | 文档永远 PENDING | 去重命中且 `status=PENDING` 时补发一次 `sendParse` |
| 消息丢失（落库后发送失败） | 文档永远 PENDING | 对账每 5 分钟补发，`retry_count` 封顶 |
| 对账与 MQ 重试叠加 | 同一文档被并发消费 | 幂等兜住；单实例下概率低；多实例明确不支持 |
| jtokkit 与 Qwen 分词偏差 | 块实际 token 少于预期 | 偏差方向是「更小」，安全；写进验证文档 |
| 按 token 切块后块数翻倍 | embedding 调用次数与成本上升约一倍 | 文档写清；需要时调 `max-tokens` |
| 不用 starter | 启停、重试逻辑要自己写对 | 启动/关闭走 `SmartLifecycle`，消费异常走 `MessageListenerConcurrently` 返回值 |
| 事务自调用 | 「每批独立事务」失效 | 拆 `DocumentChunkWriter` 独立 Bean |

## 13. 已确认的决策（2026-10-20）

| # | 决策点 | 结论 | 理由 |
|---|---|---|---|
| 1 | starter 还是原生 client | **原生 `rocketmq-client`** | starter 对 Spring Boot 4 的适配没有可靠依据；本项目 AI 接入本来也是手包的，风格一致 |
| 2 | 单 topic 还是双 topic | **双 topic**（parse / embed） | parse 吃 CPU 与磁盘，embed 吃网络；分开后重试语义、消费组、排查边界都清楚 |
| 3 | 分词器 | **jtokkit + cl100k_base** | 零 native 依赖，Windows 不折腾；`TokenCounter` 接口隔离，以后可换 DJL |
| 4 | RocketMQ Dashboard | **不做** | 先用消费日志与 `mqadmin`；真需要看图再加容器 |

前三条一旦落地，第 6 步（MQ 接入）就不再是「设计未定」，可以直接照第 4 节写。

## 14. 对齐补充（上版遗留，仍然有效）

1. **`normalized_text` 必须落库**，否则 `char_start/char_end` 没有意义、`reindex` 要重跑 Tika。
2. **重复上传的竞态**：捕获唯一索引冲突（先确认 MyBatis-Plus 是否做了 Spring 异常翻译，抛的是 `DuplicateKeyException` 还是 `PersistenceException`），回查后返回已有文档。
3. **`@Transactional` 自调用不生效**：拆独立 Bean。
4. **删除与入库互斥**：处理中删除 → 409；消费端每次写库前用 `deleted = false` 二次确认。

上线式检查：**任何一条消息被重复投递两次，结果必须与一次相同**。

## 15. 对齐结论（2026-10-20）

10 条事实核对全部成立（其中 `batch-size` 是配置项而非硬编码、`createdAt` 用 JVM 默认时区填充，均不影响本模块）。三条修正已并入正文：

| # | 问题 | 修正 | 落在哪 |
|---|---|---|---|
| 1 | 对账用 `updated_at` 会误杀正在跑的大文档，且重发 parse 会清空已回填向量 | 加 `last_progress_at` 心跳列，对账按它判活性 | 2 节 DDL、4.5 |
| 2 | 在 `create()` 事务内发消息 → 消费端查不到行 → 文档卡 PENDING；local 模式会把整条链路卷进上传事务 | 发消息移到事务提交后（controller 编排）；去重命中且 PENDING 时补发 | 4.6 |
| 3 | local 模式若同步执行，大文件演示会占住 HTTP 线程 | `LocalIngestQueue` 内部走可注入的 `Executor`（默认虚拟线程），测试注入 `Runnable::run` | 4.4 |

还需要本机确认的三件事（不影响开工）：

1. `mvn -v` —— 决定测试怎么跑；
2. `mvn dependency:tree -Dincludes=io.netty` —— RocketMQ 的 Netty 会不会被 Boot BOM 顶到 4.2；
3. `getReconsumeTimes()` 首次投递是 0 还是 1 —— 在 smoke test 里打印 `msgId + reconsumeTimes`，用实测值定条件。

**单实例限制**：多实例下同一消费组的正常投递不会重复，但对账任务会重复扫到同一批行、并发发消息；而 parse 的「先删后插」在交叉执行时会撞唯一索引，甚至产出 READY 但向量全空的文档。幂等只保证重复执行结果一致，**不保证交叉执行安全**。模块五只支持单实例，写进 known-issues。
