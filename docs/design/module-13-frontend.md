# 模块十三：前端设计稿

> 本文取代 `overview.md` 里"模块 13（不在本轮范围）"的一行占位。
> 前端不写业务逻辑，只做三件事：把后端的证据链摆到明面上、让记录这件事足够顺手、让截图能讲清项目。
> 选型、视觉、页面、交互、后端配合项以本文为准；实现时如有冲突，先改本文再改代码。

---

## 1. 立场

这个项目的前端不是"给接口套个界面"，而是产品原则的可视化：

1. **事实与推断必须在视觉上分开**，不是写在文案里，而是写在标记系统里。
2. **三源标注必须常驻可见**，不能藏在"来源"抽屉里，点开才看得到。
3. **检索过程必须可解释**：查了什么、查到几条、为什么没查到，用户随时能核对。

普通 RAG 项目的界面是一个聊天框。我们的界面是一本**带边注的记录簿**：正文是回答，边注是证据，实心是事实，空心是推断，虚线是还没被确认的猜测。这是全站唯一的设计母题，其余一切克制。

## 2. 设计系统

### 2.1 色彩

底色是账本纸的冷灰绿，不是暖米色；主强调色是苔绿，用在一处就够。

| 名称 | 值 | 用途 |
|---|---|---|
| 墨 | `#1C231F` | 正文、主要文字 |
| 纸 | `#EFF0E9` | 页面底色 |
| 帘 | `#F7F8F2` | 边注栏、输入区、次级表面 |
| 苔 | `#54663D` | 唯一主强调：主按钮、进行中、选中态 |
| 界 | `#CDD1C3` | 1px 分隔线、边框、输入框描边 |
| 弱 | `#6E7568` | 次级文字、时间戳（对比度 ≥ 4.5:1） |

来源色只用于 3px 刻度与短标签，绝不做大面积填充：

| 来源 | 名称 | 值 | 字形 |
|---|---|---|---|
| 时间线 | 时 | `#2C6B67` | 实心刻度 |
| 文档 | 文 | `#8A6E24` | 实心刻度 |
| 记忆 | 忆 | `#63538A` | 实心/空心（看记忆类型） |
| 图谱 | 图 | `#4B6472` | 实心刻度 |

颜色永远和汉字标签、刻度形状一起出现，不单靠颜色区分——色弱可用，打印截图也认得出。

### 2.2 标记系统（全站统一的语义）

这是整套设计里最不能妥协的一条，所有页面遵守：

| 形状 | 含义 | 出现位置 |
|---|---|---|
| 实心圆点 / 实线 | 用户确认过的事实（时间线记录、FACT 记忆） | 时间线条目、记忆卡片、来源刻度 |
| 空心圆点 / 细描边 | AI 推断（INFERRED 记忆、AI 总结的规律） | 记忆卡片、来源刻度、回答里的推断句 |
| 虚线 | 待确认（PENDING 记忆候选） | 记忆收件箱、边注里的候选区 |

回答正文里，凡是 AI 自己归纳、没有直接证据支撑的句子，左侧带一条 2px 宽的半透明苔色竖线；有证据的句子不带。用户扫一眼就知道哪句是"你说的"，哪句是"它猜的"。

### 2.3 字体

- **正文与回答**：霞鹜文楷 Screen（LXGW WenKai Screen），17px / 行高 1.9。楷体的手写感贴合"记录"，而且它是真正为屏幕优化的版本。用 npm 上的 `lxgw-wenkai-screen-webfont`（按 unicode-range 分片，只会下载用到的子集），不要自己切字体。
- **界面控件**：系统黑体栈（`-apple-system, "PingFang SC", "Microsoft YaHei UI", sans-serif`），13–14px。按钮、菜单、表格用黑体，阅读内容用楷体，角色分工清晰。
- **数字**：等宽数字（`font-variant-numeric: tabular-nums`），时间线列表对齐用，不额外引入等宽字体。

字号阶梯：28 / 20 / 17 / 14 / 13 / 12。正文行宽 ≤ 68 个字符。

### 2.4 布局

三栏固定结构，边注栏不是抽屉，是可折叠的第二列：

```
┌────────┬──────────────────────────────┬───────────────┐
│ 会话栏  │  正文栏                       │  边注栏        │
│ 220px  │  max 680px，居中              │  300px        │
│        │                              │               │
│ 10-22  │  10月18日 周六 · 夜跑 8km      │  证据 4 条     │
│ 10-20  │  （用户的话，20px 楷体）        │  ● 时 [T1] …  │
│ 10-18  │                              │  ● 文 [D1] …  │
│        │  回答正文，引用 [T1] 是内联小片  │  ○ 忆 [M1] …  │
│        │  · 无气泡、无头像、不分左右      │  ┈ 待确认 1    │
│        │  ─────────────────────────    │  ─ 检索详情 ▾  │
│        │  [ 记一笔，或者问点什么        ] │               │
└────────┴──────────────────────────────┴───────────────┘
```

边界处理：< 1100px 边注栏收成正文右下角的悬浮"证据 4"按钮，点开侧滑；< 760px 会话栏改为顶部汉堡菜单。

**不做的事**（都是"一看就是模板"的默认，逐条避免）：聊天气泡与头像、来源做成等宽卡片网格、首页大号数字加渐变、全大写小标签、`AI · 助手` 这类中点拼接元信息、"→"结尾的按钮文案。

## 3. 页面

### 3.1 对话页（默认页）

**结构**：左会话列表 / 中正文流 / 右边注。

一轮对话就是一段文档：

- 用户提问：楷体 20px，上方一行 12px 弱色时间（`10月18日 周六 21:34`），像日记的小标题。
- 回答：正文流式渲染，Markdown 正常渲染；`[T1]`、`[D1]` 不在正文里显示成方括号文字，而是渲染成 18px 高的内联小片：`时1`（浅底、来源色文字）。悬停展开原文片段，点击跳到对应记录或文档块。
- 轮次之间只有一条 1px 浅色分隔线，距离 40px。

**边注栏**在回答开始生成前就已经出现，这是关键：

1. `event:start` 到达后，边注栏进入"检索中"状态：四个来源各一行（时 / 文 / 忆 / 图），每行一个呼吸的苔色细条。
2. 研究阶段（可能几秒到十几秒）有 `event:step` 时逐条追加 `时 search_timeline "上个月跑步" · 3 条`，没有时按时间推进文案"仍在检索，已 8 秒"。
3. `event:sources` 到达，边注栏自上而下依次"落笔"（每条间隔 40ms 淡入），这个动作全站只发生一次，是唯一允许的编排动画。
4. 同时正文开始出字。

边注栏底部是折叠的"检索详情"，展开后是一张小表：时间窗、命中 / 检索 / 纳入、被预算丢掉几条、文档是否降级及原因。`documentSearched=true` 且 `documentsRetrieved=0` 时在这行末尾补一句"文档里没查到相关内容"——`known-issues.md` 第 4 条的待办就落在这里。

**输入区**：单行自适应高度的 textarea，占位文案「记一笔，或者问点什么」。Enter 发送，Shift+Enter 换行。发送后发送键变成"停"（方形），点击走 abort，后端靠连接断开感知取消。

**首条消息**：`conversationId` 为空时直接发，后端在 `event:start` 里回传新建的会话 id，收到后刷新左侧列表并高亮。不要先建空会话。

**错误**按 `errorType` 分别处理，不共用一句"出错了"：

| errorType | 文案 | 操作 |
|---|---|---|
| NOT_CONFIGURED | 还没配置模型 key，检索和生成都不可用 | 显示配置说明链接 |
| AUTHENTICATION / INSUFFICIENT_BALANCE | key 无效或额度不足 | 同上 |
| RATE_LIMITED | 请求太频繁，稍等几秒 | 提供"重试" |
| TIMEOUT / NETWORK / UPSTREAM_ERROR | 模型暂时没响应 | "重试"，保留问题原文 |
| STREAM_INTERRUPTED / BAD_RESPONSE | 回答中断了（partial=true 时保留已出文字） | "继续问" |
| INVALID_REQUEST | 问题太长（64–4096 tokens 限制） | 原地提示 |

503（key 未配）可能在建流之前就返回，接口返回的是统一 `ApiResponse`，不是 SSE，前端要同时处理两种失败形态。

### 3.2 时间线页

按日期浏览的列表，每条记录一行，时间显示在左侧。

**记录列表**

- 每条格式：`21:30` · 内容 · 标记形状（持续事件显示 `21:30–23:00`，进行中显示 `21:30 →`，虚线末端一个呼吸的实心点）。
- 悬停显示编辑/删除操作，点击展开行内编辑，不跳页。
- 按天分页，翻页用"前一天 / 后一天"按钮，不做无限滚动——时间线需要确定的位置感。
- 时区：一律用浏览器本地时区显示，请求边界用带偏移的 ISO 串（`2026-10-22T00:00:00+08:00`）。依赖 `fix/timeline-utc` 分支合入（见 §5.4）。

**新建 / 编辑表单字段**

内容输入框（主字段，自动获焦），加上以下时间字段：

```
开始   [今天] [昨天] [前天] [其他…]   [21] 时 [30] 分
结束   [今天] [昨天] [前天] [其他…]   [21] 时 [30] 分   [进行中]
```

字段规则：

- 日期默认今天；三个快捷标签（今天 / 昨天 / 前天），选中态苔色背景；"其他…"展开月历。
- 时/分拆成两个固定宽度的数字输入框，只接受数字，填完 2 位自动跳焦点，失焦后补零（`9` → `09`）。
- 开始时间默认当前时刻（1 分钟精度）；**结束时间默认等于开始时间**（瞬时事件）。
- 开始时间改变时，若结束仍等于旧开始，自动跟随；用户手动改过结束后两者脱钩。
- 勾选"进行中"：结束字段禁用变灰，end = null（进行中）。进行中是主动选择，不是默认。
- 提交时校验：结束 < 开始 → 行内报错"结束时间不能早于开始时间"，不自动修正。

**快速记一笔（顶部常驻）**

一行：内容输入框 + 时间默认当前（start = now，end = start，即瞬时事件）+ 保存键。Enter 触发保存。这是最高频操作，零跳转。保存后记录出现在列表顶部。如果用户想记进行中的事件，需要展开表单勾选"进行中"。

**进行中的条目**

进行中条目（end = null）在列表里带虚线和呼吸点（`prefers-reduced-motion` 下静止），旁边只有一个操作："填写结束时间"，点击后展开结束时间字段，默认填入当前时刻，一键保存。

### 3.3 记忆页

三态在版面上直接铺开，不做 tab 切换——用户需要同时看见"有哪些事实"和"还有多少没确认"。

```
┌─────────────────────────────┬──────────────────────────────┐
│ 待确认 4                     │ 已确认                        │
│ ┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈  │ ● 事实 12    ○ 推断 5          │
│ ┈ AI 推断：习惯晨跑，通常 7 点  │ ● 每天早起跑步，周末在公园      │
│   证据：10-18 夜跑 · 10-20 …  │   来源 对话 10-18             │
│   [确认] [改成事实] [拒绝]     │ ○ 最近在准备 Java 面试          │
└─────────────────────────────┴──────────────────────────────┘
```

- 每条候选必须展示 evidence：来源类型、时间、原文摘录，一行内可展开。
- "确认"落到 `proposedType`（后端已支持），"改成事实"是显式覆盖（需要后端配合，见 §5.3）。
- 已确认区按"事实 / 推断"两列或两组，标记形状沿用 §2.2。推断不是贬义，只是未经验证，配色不做得像警告。
- 删除操作二次确认，不用弹窗，用行内"确认删除?"两步按钮。

### 3.4 文档页

- 顶部上传区：整块可拖拽，虚线边框，拖入时变实线。支持多选，逐个显示进度。
- 列表：表格式但无竖线，行高 56px。列：标题、类型、状态、块数、更新时间、操作。
- 状态是四段进度而不是一个色块：`PENDING → PARSING → EMBEDDING → READY`，当前段苔色实心，已完成段细线，失败（FAILED）整条变灰并在行内展开 `errorMessage`。
- 非 READY 的行右侧提供"重建索引"（`POST /{id}/reindex`）；上传后每 3 秒轮询列表，全部 READY/FAILED 后自动停。
- 详情抽屉：左侧标题与元信息，右侧块列表（分页 20），每块显示 heading 面包屑与字符数；被引用跳转时，目标块滚动到位并短暂高亮 1.5 秒。
- `chunkTruncated=true` 的文档在标题旁标一个"只覆盖前 2000 块"，把 `known-issues.md` 第 5 条摆到用户面前。

### 3.5 图谱页（可选，最后做）

搜索一个实体，返回一跳内的三元组，用力导向图或简单的放射状布局渲染；节点点击展开关联文档。截图效果好，但优先级低于前四页——先把带边注的对话页做扎实。

### 3.6 状态与设置页

一页纸：`/api/health` 的数据库与 pgvector 状态、模型是否已配置（用一次有意的最小请求判断，或直接读错误码）、技能列表（`/api/skills`，可热重载）、当前版本与构建时间。面试时打开这一页，能直接回答"怎么确认它真跑起来了"。

## 4. 实现约定（指导，不代写）

### 4.1 目录与依赖

```
frontend/
  src/
    app/            # 路由、全局 Provider、主题 token
    features/
      chat/         # 会话列表、正文流、边注栏、SSE 解析器
      timeline/
      memory/
      documents/
      graph/
      status/
    components/     # 标记系统、来源小片、空态、错误块
    api/            # 请求封装、类型定义（与后端 DTO 一一对应）
```

- Ant Design 6 + `@ant-design/x` 2（X 2.x 的 peer 依赖要求 antd 6，不要混搭 antd 5）。X 负责气泡以外的通用能力：`Sender`、`XMarkdown`、`Think`、`useXChat` 可按需取用，但**不要用它的默认气泡布局**——视觉按 §2.4 自定义。
- antd 主题只改 token：`colorPrimary` 取苔，`colorBgBase` 取纸，`colorTextBase` 取墨，`borderRadius` 统一 4px（不是 8，账本不是 App）。组件库的味道主要来自圆角和阴影，这两项压住，观感立刻不同。
- 服务端状态用 TanStack Query；SSE 流状态用 `useReducer` 单独管理，两者不要混在一个 store 里。
- 路由：React Router，四个主页面 + 详情抽屉（用 search param 表达，便于截图和回链）。
- 安装时以当天 npm 最新稳定版为准并锁进 `package-lock.json`；不追 beta。

### 4.2 SSE 客户端（最容易出错的地方）

`POST /api/chat/stream` 不能用 `EventSource`（只支持 GET）。用一个 60 行左右的 `fetch` + `ReadableStream` 解析器，必须处理：

- 事件块以空行分隔，`event:` 与 `data:` 可多行 `data:` 拼接；
- 忽略以 `:` 开头的注释行——后端每 15 秒发 `: ping` 心跳，解析器不处理会崩；
- 兼容 `\r\n`；用 `TextDecoder(stream: true)` 处理跨 chunk 切断的中文；
- `AbortController` 绑定"停"按钮；abort 后不重连、不重试；
- 收到 `event:sources` 前是"检索中"，收到后切"生成中"；`done` 之后才允许发下一条；
- 超过 40 秒没有任何字节（包括心跳）判为卡死，提示"连接好像断了"，提供重试。

事件契约（当前后端已实现，顺序是不变式）：

```
start   {requestId, conversationId}
sources {items[], retrieval{...}}      ← 固定在第一个 delta 之前
delta   {content}
done    {finishReason, usage}
error   {code, errorType, message, partial, requestId}
```

加 `event:step` 之后（§5.1），step 出现在 `start` 与 `sources` 之间。前端解析器按"未知事件忽略"写，以后加事件不用改。

### 4.3 引用渲染

回答里把 `[T1]` 解析成片段时，只认 `sources.items` 里真实存在的 ref，其余原样显示（模型偶尔会编编号，正好暴露）。小片点击的行为：timeline → `/timeline?date=…&focus=id`；document → `/documents?open=id&chunk=chunkId`；memory → `/memory?focus=id`；graph → `/graph?entity=…`。所有跳转都是前端路由，不整页刷新——演示时流畅度即专业度。

Markdown 渲染开启 raw HTML 过滤，外链 `rel="noopener noreferrer"`。回答内容来自模型，一律当不可信文本。

### 4.4 质量底线（验收时逐条过）

- 键盘可达：Tab 顺序合理，焦点环可见（2px 苔色，不用 `outline:none`）。
- `prefers-reduced-motion` 下关闭边注落笔与呼吸动画。
- 三种状态都要写：加载、空、错。空态给下一步动作（"还没有记录，记下今天第一件事"），错误说清原因与退路。
- 390px 宽度下能用：边注变抽屉，时间尺可横向滚动。
- 截图检查：1440px 与 390px 各截一次，截图里不能出现浏览器默认滚动条、未加载的字体、Lorem 文本。
- 不引入暗色模式。这个设计是纸面的，暗色是另一套设计，等主链路稳定再说。

## 5. 需要后端配合的事项

按优先级排列，前四条不做，前端体验会明显缺一块。

### 5.1 `event:step`：把 Agent 的检索过程流式吐出来（必须）

现状：`start` 之后到 `sources` 之间最长可能十几秒完全静默（研究阶段跑 ReAct），用户只能盯着空屏；`ChatAgentTools.recordToolCall` 只记了次数，没有结构化输出。功能清单写的"流式 + 思考过程"目前只兑现了前半句。

建议在 `ChatAgentTools` 每次工具调用结束时向 `AgentSseSession` 发一条：

```
event: step
data: {"seq":3,"tool":"search_timeline","query":"上个月跑步","hits":3,"ok":true,"ms":412}
```

顺序约束：全部 step 在 `sources` 之前发出；`sources` 仍固定在第一个 `delta` 前。工具名已有注解（`search_timeline`、`get_timeline_by_date`、`search_documents`、`search_memory`、`search_graph`、`propose_memory`），`query` 取入参，`hits` 取工具返回的条数，失败时 `ok=false` 并带上简短原因。不要发模型原始思维链，只发"调了什么、查到几条"——既够解释，也不泄露 prompt。

### 5.2 补齐 `SourceItem` 上"记忆类型"和"图谱文档归属"（必须）

产品原则要求"对话里区分事实与推断"，但 `EvidenceItem.toSourceItem()` 对 memory 走的是 6 参构造，`title`（记忆类型）和 `score`（置信度）被丢掉了；graph 也只带了边 id，`GraphHit.documentId` 没进 sources。结果：前端拿到的记忆来源无法标注 FACT / INFERRED，图谱引用无法跳回文档。

建议：`SourceItem` 增加两个可空字段 `memoryType`、`documentId`（记忆填前者，图谱填后者，时间线/文档为 null），现有构造器保留默认值。改动小，但对"事实/推断分离"这条核心卖点影响最大。

### 5.3 确认记忆时允许修改内容（建议）

`POST /{id}/confirm` 目前无 body，用户只能"原样确认"或"拒绝"。更好的产品行为是"确认并顺手改措辞"。建议接受可选 body `{"content": "..."}`，空则沿用原内容；`propose_memory` 生成的 60 字摘要，人改一遍再入库的质量会高很多。

### 5.4 合并 `fix/timeline-utc`（必须）

该分支（响应统一 UTC、PUT 支持清空 end_time）一直没合进主线。前端到时区换算完全依赖响应语义：请合入并约定**所有时间字段都是带偏移的 ISO-8601**（UTC 或 +08:00 都可，前端用 dayjs 转本地），`start`/`end` 查询参数接受同格式。顺带确认 `end_time` 显式传 `null` = 进行中，这个语义前端要靠它画虚线段。

### 5.5 引用跳转定位（建议）

点击文档引用时，需要把 `chunkId` 定位到分页里的那一块。现在只有 `GET /{id}/chunks?page&size`，前端得逐页找。建议加 `GET /api/documents/{id}/chunks/{chunkId}`（返回该块 + 前后各一块），或给列表接口加 `aroundChunkId` 参数。

### 5.6 部署与跨域

推荐**同源部署**：Vite 开发时 `/api` 代理到 `localhost:8080`，生产用 nginx 托管静态文件并把 `/api` 反代到后端，docker-compose 多一个 frontend 服务。这样后端一行 CORS 配置都不用加。
如果坚持前后端分域，需要加全局 CORS（允许 `POST`、`GET`、`PUT`、`DELETE` 与自定义头），并注意 SSE 不能经过会缓冲响应的反向代理——后端已经发了 `X-Accel-Buffering: no`，nginx 侧仍需 `proxy_buffering off; proxy_read_timeout 300s;`。

### 5.7 可选

- `springdoc-openapi` 暴露 OpenAPI，前端用 `openapi-typescript` 生成类型，`api/` 目录不再手抄 DTO。工作量小，且是面试可讲的工程化细节。
- `MessageResponse.sources` 目前是 JSON 字符串，保持即可，前端解析；不必改后端。
