# 项目现状与横向对比（2026-10-20）

> 自评文档，回答两个问题：**做到哪了**、**和市面上的知识库对话 Agent 差在哪**。
> 数据来源：仓库代码、`docs/verification/*.md`、`target/surefire-reports`、`git log`。所有数字均可复现，口径写在各节。

---

## 1. 一句话结论

**工程底座已经到了「能拿得出手」的程度，产品形态还停在「一条单源 RAG 闭环」。**

按 `docs/design/overview.md` 的 13 个模块算，完成度 **4/13（约 31%）**。
但这不是「做完 31% 的 Dify」——两者坐标系不同：Dify / FastGPT / RAGFlow 是**平台**（广度优先，给一堆人自助搭建），本项目是**单用户的个人上下文 Agent**（深度优先，一个场景做穿）。用平台的功能清单去衡量它，只会得出「全面落后」的错误结论。

真正的判断是：

- 在 **LLM 接入 + 流式工程 + 失败语义** 这一层，本项目比多数 RAG demo 扎实，部分细节（SSE 取消竞态、连接阶段才降级、连接类 DB 异常才 503）已经超过「教程级」水准。
- 在 **知识库本体**（文档入库 → 解析 → 分块 → 向量 → 混合检索 → rerank）这一层，**目前是 0**。项目名字里的「知识库」还没落地，现在只有「时间线」一个知识源。
- 在 **产品形态**（多轮、前端、评测、可观测）这一层，**目前基本是 0**。面试官现在只能 curl。

一句话给面试场景：**「我把 RAG 最脏最难的边界条件做对了，但还没把 RAG 最常见的部分做出来。」**

### 2.3 现在真正能跑通的链路

```
POST /api/chat/stream {"question":"我上周做了什么？"}
  → 无 key 预检（503/50301，不查库、不开流）
  → TimeWindowParser：中文时间表达 → 半开区间（今天/上周三/最近 3 天/2026-10-17/去年10月…，365 天夹紧）
  → KeywordExtractor：只抽引号短语 + ASCII 词（不猜中文分词）
  → TimelineRetriever：区间重叠 SQL + 关键词（词边界 / ILIKE 转义）+ 0 命中自动回退一次
  → ContextAssembler：40 条上限 / 8000 字总预算 / 先单条截断再丢整条 / 单日等距抽样 / T1..Tn 编号
  → ChatSseService：start → sources → delta* → done | error，15s 心跳
  → 失败路径：无 key 503、停库 503、401/429/5xx 分类、断流 partial=true、客户端取消 3s 内关闭上游
```

本机已实测通过（`docs/verification/04-closed-loop.md` 3.2–3.6）：无 key 503 且不建流、停库 503 且不建流、无命中时不编造并建议扩大范围、`sources` 时间统一 `+08:00`、`timeout 3 curl` 后日志出现 `SSE cancelled` 且上游关闭。

### 2.4 工程上真正做完的细节（对比时不要自谦的部分）

这些是「看起来简单、写起来全是坑」的东西，也是面试时最能聊的素材：

1. **SSE 取消与写入共用一把锁**：`SseSender` 在 cancel 置位后拒绝新的 send，堵住「`hasNext` 返回 true → send 之前」的窗口；`onCompletion/onTimeout/onError` 三条路径统一清理，`close()` 幂等。
2. **四层超时**：连接 5s / idle 30s（有事件到达就续命）/ 首包 60s / 总 180s。首包前不因 idle 误杀，这在真实模型冷启动时会踩。
3. **只在连接阶段降级**：`FailoverChatClient` 一旦 `stream()` 返回就不再换模型，避免已经吐给用户的内容重来一遍。这个决定比「无脑重试」正确得多。
4. **错误语义分层**：无 key 在检索前预检 → HTTP 503（而不是 200 之后再 SSE 里报错）；停库靠 `MyBatisSystemException` 根因识别 SQLState `08xx`/`57P0x` 才判 503，SQL 语法错误仍 500——没有把所有 MyBatis 异常都当「数据库挂了」。
5. **上下文预算是有序的**：先 500 字、再 300 字、再丢整条；单日窗口等距抽样保全天两端，多日窗口从最旧丢。这是「上下文工程」的具体化，不是 `String.join` 前 4000 字。
6. **Prompt 与 sources 同源**：编号在 `ContextAssembler` 同一个循环里生成，从结构上杜绝「正文引了 T3，sources 里没有 T3」。
7. **拒绝过度聪明**：中文不做分词（没有分词器时抽错比不抽更糟）；时间表达规则匹配、解析失败回落默认窗口、不报错；关键词 0 命中只回退一次且不改时间窗。这类「克制」在 code review 里是加分项。

## 3. 坐标系：两类不同的产品

把本项目和 Dify 们放在一张功能表里比是没意义的。先分清三类：

| 类别 | 代表 | 卖点 | 衡量标准 |
|---|---|---|---|
| **平台型** | Dify、FastGPT、RAGFlow、MaxKB、Coze、百炼 | 让**别人**自助搭出无数个知识库应用 | 功能覆盖广度、接入生态、多租户、可视化编排 |
| **框架型** | Spring AI、LangChain4j、LlamaIndex、LangChain | 让**开发者**少写胶水代码 | 抽象完整度、生态、可组合性 |
| **应用型（本项目）** | 个人上下文 Agent、Glean / Notion AI 这类个人/企业助手 | **一个具体的人**的上下文，做得足够深 | 这个场景是否真的被解决、边界是否可靠 |

本项目在第三类。所以正确的对比对象不是「Dify 有没有这个功能」，而是：

1. 平台型产品**不会做**的能力，你有没有做出来（这是差异化）；
2. 应用型产品**必须做**的能力，你缺了没有（这是短板）。

## 5. 判断：三层差距，优先级完全不同

### 5.1 第一层：已经超纲的部分（别再加码）

LLM 接入抽象、SSE 生命周期、错误分类、降级策略、上下文预算、时间表达解析。这一层的完成度已经高于绝大多数同规模 RAG demo，**继续打磨的边际收益很低**。模块 9 再回头做融合重排是对的，现在不要动。

### 5.2 第二层：让它「名副其实」的最小集合（必须做）

按投入产出排序：

1. **模块 5 + 6：文档入库 + 双路检索**（约 2 个模块的工作量）
   没有这一步，「知识库对话 Agent」这个 title 站不住。做的时候只要支持 PDF/Markdown/TXT 三种格式 + Tika 解析 + 递归分块 + `text-embedding-v4` + pgvector `<=>` 余弦 + 「向量 ∪ 关键词」简单合并即可，**不要一上来做父子分块和 rerank**（那是模块 9 的事）。
2. **模块 10 的「多轮」部分**（可以提前，和模块 6 并行）
   只做最朴素的：`conversation` + `message` 两张表 + 最近 N 轮拼进 prompt + 简单指代改写。不需要摘要、不需要记忆三态。**这一项的体验提升远大于它的实现成本**，而且能把「那第二天呢」这类演示问题救回来。
3. **模块 13 的「最小前端」**（强烈建议提前到模块 6 之后）
   现在整个项目对外只有一个 curl 和一堆 markdown。简历项目三价值里「可展示」是第一条，而展示成本最低的做法是：一个页面 = 输入框 + 流式输出 + 引用卡片（点击跳时间线/文档）+ 时间线列表页。用 React + SSE 大概 1–2 天。**没有它，前面 4,000 行代码在面试里只能靠嘴说。**

### 5.3 第三层：差异化，现在只在文档里（最该警惕的部分）

`overview.md` 里写得很清楚的三条原则——事实/推断分离、记忆需确认、三源分别标注——**目前只有第一条真正落了代码（prompt 里的一段话）**，另外两条连表都没有。而这恰恰是与 Dify/FastGPT 拉开距离的唯一理由。

如果模块 5–13 只是把通用 RAG 的功能补齐，那这个项目最终会变成「一个功能更少、但文档写得更好的 Dify」，差异化叙事就失效了。建议在模块 6 之后插入一个**最小记忆闭环**（哪怕只有 `memory` 表 + PENDING 确认接口 + 注入 prompt 三条），让「AI 提出记忆 → 用户确认 → 变成事实」这条链路能被演示出来——**这一个动作的展示价值，可能高于模块 7 的知识图谱**。

### 5.4 关于「手搓 vs 框架」

不用 Spring AI / LangChain4j 是明确决策（`overview.md` 第 6 节），学习价值成立。但面试时会被问「为什么不用」，标准答案不是「我想学」，而是：

> 我需要控制 SSE 的取消语义、首包超时和降级时机，这些框架给的是默认值，而这个项目的失败路径是核心需求。

这个回答成立。但要注意两个风险：一是**别在简历上写「自研 RAG 框架」**（会招来「重复造轮子」的质疑），二是**接口划分要向框架靠**（`ChatClient` / `ChatMemory` / `ContentRetriever` / `Advisor` 这套命名是对的，说明你理解生态，而不是闭门造车）。

## 6. 下一步：建议的优先级

原计划的 13 个模块顺序基本正确，只建议五处调整：

| 建议 | 理由 |
|---|---|
| **先提交模块四**（拆成 2–3 个 commit：检索 / 组装 / SSE+文档），再开模块五 | 1,500 行未提交改动是当前最大风险 |
| **模块 6 之后插入「最小前端」**，而不是等到模块 13 | 可展示 > 完整度。录一段 3 分钟演示视频，比多写两个模块有用 |
| **模块 6 之后插入「最小评测集」**（15–30 条 golden 问题 + 召回率/引用正确率/拒答率三个指标） | 这是唯一能证明「检索质量」的东西，也是主流产品都在做、而个人项目普遍缺失的部分。成本约半天，收益在面试里极高 |
| **模块 7（知识图谱）可以降级或延后** | 对 demo 和面试的加成明显低于记忆闭环与评测；Neo4j + LightRAG 的工程复杂度不低 |
| **模块 12（ReAct + MCP）保持在后** | 没有多轮和工具的基础，ReAct 做出来也不好看 |

调整后的建议顺序：

```
4（提交）→ 5 文档入库 → 6 双路检索 → [前端最小版] → [评测集] → 10 多轮+记忆最小闭环
→ 8 意图路由 → 9 融合重排 → 12 ReAct/MCP → 7 图谱（可选）→ 13 前端完整版
```

## 7. 结论

- **做过的东西是真的做完了**：4 个模块，约 120 个测试，真实 key / 停库 / 取消都实测过，工程细节经得起追问。这一层不需要自卑。
- **没做的东西是真的没有**：文档、向量、多轮、记忆、前端、评测——六个「0」。其中**文档 + 多轮 + 前端**决定了它现在配不配叫「知识库对话 Agent」，**记忆 + 事实/推断分离**决定了它配不配叫「懂你的」。
- **对比市面产品的正确姿势**：不比功能数量（永远输），比「平台做不到的那个场景，你做到了没有」。现在的答案是「设计里有，代码里还没有」。
- **最紧急的不是加功能，是提交代码 + 做一个能看的界面**。

差距客观存在，但方向是对的：市面上的平台解决的是「让所有人搭知识库」，你要解决的是「让一个人被自己记住」。前者已经卷成红海，后者还没人认真做。
